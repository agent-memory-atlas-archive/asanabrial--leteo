# Leteo against Engram, measured

Leteo is a reimplementation of Engram, and that sentence — plus the attribution
in [`NOTICE`](../NOTICE) — is usually the whole of the comparison a reader sees.
This page is the measurement behind it. It is deliberately narrow: the same
synthetic corpus is saved into both engines, the same questions are put to each
engine's own MCP `mem_search`, and the answers are scored. It is not a claim
about which product is better to use; it is what one harness measured on one
day, with the versions it names.

The numbers and versions below are generated by
[`tools/engram-bench/compare.py`](../tools/engram-bench/compare.py) from the
harness's own output. They are not typed into this file: re-running the command
on a machine with a different Engram, or after a new Leteo commit, rewrites the
generated block with what it actually measured. If a step cannot run, the block
says it was skipped rather than showing a number nobody produced.

## The corpus

[`tools/engram-bench/comparison_corpus.py`](../tools/engram-bench/comparison_corpus.py)
builds a deterministic corpus — a fixed seed, no network — of synthetic memories
in two projects, `alpha-api` and `beta-web`, and a set of queries each of which
has exactly one memory it should find.

It is **held out from the ratchet**. `ratchet.py` gates search quality on
[`corpus.py`](../tools/engram-bench/corpus.py), a different corpus whose
paraphrases avoid the target's words and whose partial-word queries give a
fragment; a benchmark that is also the tuning set cannot tell overfitting from an
improvement. The queries here were written for the comparison and raise or lower
no floor in `floors.json`, and `tests/repository_guards.rs` refuses a commit that
edits this file together with `src/store/search*` or `src/store/semantic*`, so a
ranking change cannot be tuned against the corpus that is meant to measure it.

Most of the queries share a distinctive word with the memory they should find, so
a plain keyword match can answer them and the relaxed stages are not the only way
through. The queries are still synthetic and were written knowing how both
engines search — see [Caveats](#caveats).

The memory and query counts are printed in the generated block from
`comparison_corpus.py` itself, so they cannot drift from what the harness ran.

## The method

Each engine answers through its **own MCP `mem_search`**, started by
[`tools/engram-bench/mcpclient.py`](../tools/engram-bench/mcpclient.py) with
`HOME` and the data directory pointed under a temporary `BENCH_STATE`, so a run
cannot reach a real store. Every query is asked at the limit the harness fixes and
the generated block names, with the engine's defaults; the target's rank is its position in the returned ids, and the metrics
are hit@1, hit@5 and mean reciprocal rank (MRR), per query kind and overall.

The Engram side is saved through Engram's own `engram save` CLI, so its own write
path builds its index; a copy of that store is then adopted with
`leteo import --from-engram`, and ids survive adoption, so one answer key serves
both engines. The Leteo side is the binary built from the commit named in the
generated block.

The page reports the version of Engram that was **actually measured**, whatever
it is. Engram changes its search behaviour between releases, so a run on a
different Engram is a different measurement: the numbers belong to the version
beside them and to no other.

## Where each engine leads

The generated block computes a **leader** for every query kind, under each
engine's own defaults and again under Engram's opt-in relaxed mode. Read those
rows as what they are rather than as a general verdict.

A `tie` is an exact equality, not a closeness test, and a row where one engine
leads by a little is not a durable lead: the per-kind rows have few queries (see
[Caveats](#caveats)), and a stage change moves them. The numbers belong to the
Engram version beside them — a run on a different Engram says what that version
does.

## Reproduce it

One command, from the repository root, with the Leteo binary built from the
commit under test:

```sh
cargo build --release
LETEO_BIN=target/release/leteo python3 tools/engram-bench/compare.py
```

It rewrites this page's generated block and prints the harness output it came
from. It needs `engram` on `PATH` (or `ENGRAM_BIN` pointing at it) and stock
`python3`. `bench_cost.py` additionally needs `ENGRAM_SRC`, Engram's source tree,
for the session-start hook script that is not part of Engram's binary; without it
that step is skipped and the block says so. Set `BENCH_STATE` to reuse a scratch
directory instead of a fresh temporary one.

## Caveats

- **The corpus is synthetic.** It is held out from the ratchet, so the ratchet
  does not tune against it, but its queries were still written knowing how both
  engines search. Questions real agents asked would be a stronger test.
- **Per-kind rows have few queries.** A kind with a handful of queries moves by a
  whole rank on one answer; read the overall row and the kind counts together,
  and treat a per-kind lead of one query as noise.
- **Precision is measured only on unanswerable questions.** The no-answer
  precision counts the replies to questions the store cannot answer that came
  back empty or carried a caveat; it does not measure whether the results an
  engine does return are the right ones.
- **One machine, one day.** Timing is printed and never gated: it does not
  transfer between SQLite builds, and ranking does. The ranking numbers transfer
  better than the milliseconds.
